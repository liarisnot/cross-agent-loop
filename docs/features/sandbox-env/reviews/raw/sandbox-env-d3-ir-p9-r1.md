## Blockers

**1. Severity: Blocker — `Invoke-SandboxCommand` cannot do its own steps under the one-way module rule**
**Affected scope:** Rules *Modules* (line 262), Rules *`Invoke-SandboxCommand`* (line 283); Files row `Sandbox.psm1` (line 291)
**Finding & Guidance:** Line 262 fixes the import graph: `SandboxEnv.psm1` imports `Sandbox.psm1`, never the reverse, and `delegate.ps1` "imports both and passes environment paths and variables into `New-SandboxRun`". Line 283 then gives `Invoke-SandboxCommand` — which lives in `Sandbox.psm1` — a sequence whose first and third steps are "run the readiness gate" and "link", both of which are functions of `SandboxEnv.psm1` (Files row 289: "readiness gate, link and unlink"). `Sandbox.psm1` therefore has to call into a module it is forbidden to import. The plan gives no seam, and the two obvious answers (pass `[scriptblock]`s in; or move the gate/link out of `Invoke-SandboxCommand` and let `delegate.ps1` orchestrate) are different designs with different signatures and different test placement. Required: pick one and write it — e.g. `Invoke-SandboxCommand` takes `-TestReady` and `-Link` scriptblock parameters supplied by `delegate.ps1`, or `Invoke-SandboxCommand` takes `-EnvPaths`/`-EnvVars` already computed by `delegate.ps1` and does no gate. Name which module owns `environment-missing`'s early return in each case, since that decision drives whether `Invoke-SandboxCommand`'s Pester case needs `SandboxEnv.psm1` loaded.

**2. Severity: Blocker — Three rules depend on TOML parsing and the plan names no parser**
**Affected scope:** Data *Identity hash* (line 188), Rules *Interpreter* (line 265), Rules *Project path (D7)* (line 273)
**Finding & Guidance:** The hash includes "every workspace member's `pyproject.toml` (members are the paths matched by `[tool.uv.workspace] members` in the root `pyproject.toml`)"; the interpreter request comes from "`requires-python` from `uv.lock`, or from `pyproject.toml`"; and the `.pth` is written "for the project and each workspace member with a `[build-system]`". All three are TOML reads inside PowerShell. There is no TOML parser in this repo — no module, no helper, nothing under `skills/delegate/scripts/` (only `Sandbox.psm1`/`SandboxNative.cs`), and `scripts/test.ps1` imports nothing beyond Pester. The standard forbids leaving the choice of a dependency to the implementer, and the plan does not say "regex-match these three keys" either. Note also that the members glob must be resolved against the ref's tracked paths (`src/*` style), which is a second unspecified step. Required: either state the exact extraction method for each of the three reads (key, section, quoting rules, glob expansion against `git ls-tree` output), or add a `SandboxEnv.psm1` private `Get-TomlValue` helper to the Files row with its supported syntax enumerated and one Pester case per key.

**3. Severity: Blocker — `requires-python` is a specifier, not a version request, and is passed straight to `uv`**
**Affected scope:** Rules *Interpreter* (line 265); "What a project is" (line 73); Verification item 1 (line 311)
**Finding & Guidance:** The rule says the request is "`.python-version` (as written: `3.12` or `3.12.7`); otherwise `requires-python` from `uv.lock`, or from `pyproject.toml`", and that "at build, `uv python install "<request>"` then `uv python find --managed-python "<request>"` give the exact version". A `requires-python` value is a PEP 440 specifier (`>=3.11,<4`, `~=3.12`, `==3.12.*`), which is not a version request that `uv python install` accepts; and even if it did, the design does not say whether the low or the high end of the range is chosen. That choice is exactly what determines which wheels the estimate sums (line 267) and which interpreter folder is granted (line 280). `unsupported (python-version-unknown)` covers only "there is no request", so nothing covers an unparseable or unsatisfiable specifier either. Required: state the conversion — for example "`requires-python` selects the **lowest** version in the range that the plan supports (3.11/3.12/3.13/3.14); the request passed to `uv` is that `major.minor`", plus what happens on `>=3.9` (below any managed Python) and on `==3.12.*` — and either add a `python-version-unsupported` reason or say that an install failure surfaces as `install-failed`.

**4. Severity: Blocker — The gate hashes one ref and linking hashes another, and the mismatch is not a failure**
**Affected scope:** Rules *Readiness gate* (line 278), Rules *Linking* (line 279), Data *Identity hash* (line 188 last sentence), Components (line 92), Files row `delegate.ps1` (line 290)
**Finding & Guidance:** The gate "computes the projects and their hashes at the base ref". The hash rule says blob ids are taken "at the ref, or at the worktree's `HEAD` when linking", and linking junctions "the environment matching that worktree's lockfile (D8), when it is `ready`" (line 92). Those two refs are equal only for a freshly created worktree: `delegate.ps1` reuses an existing worktree (`if (-not (Test-Path $wt))`, `delegate.ps1` line 361) whose `HEAD` is whatever it was created at, while `-Base` is whatever the lead passed this time. The design's stated behaviour for "linking finds no `ready` environment for the worktree's `HEAD`" is a silent skip — no junction, no `.venv`, no error — which is the opposite of G5's fail-closed promise, and it produces a worker that fails its tests with a confusing Python error instead of `sandbox: environment not ready`. Required: make the two refs identical by definition (state that the gate hashes the same commit linking will use — the worktree's `HEAD` after creation, or the branch tip for a reused worktree — and that a mismatch therefore cannot arise), or state that linking raises `sandbox: environment not ready: <project>` and where that error goes for a run that already has a worktree (it must unlink and remove the worktree, since `Fail` leaves one behind otherwise).

## Majors

**5. Severity: Major — `Get-CommandPath` does not exist anywhere in the repo**
**Affected scope:** Rules *`uv` calls* (line 263); Files row `SandboxEnv.psm1` (line 289)
**Finding & Guidance:** "`$script:UvPath` (set from `Get-CommandPath uv`, or from `XAGENT_UV_PATH` when set)". There is no `Get-CommandPath` in `Sandbox.psm1`, `delegate.ps1` or `feature.ps1`; the repo's existing idiom is `(Get-Command $cmd -ErrorAction Stop).Source` (`feature.ps1` line 3123). Either the plan adds `Get-CommandPath` as a new private function (then it belongs in the Files row and in the `-UvProbe`-style test seam), or it names the existing idiom. Also unstated: whether `uv` is looked up once per module load or per call, and the exact `uv`-missing predicate, which `status unsupported (uv-missing)` (line 266) and the doctor check (line 297) both depend on.

**6. Severity: Major — Prune's "no existing worktree holds a junction to it" has no mechanism, and nothing protects a live run**
**Affected scope:** Rules *Prune* (line 277), Risks "Prune races a run that is linking" (line 117), Data *Last use* (line 215)
**Finding & Guidance:** The `linked` stamp is "an empty file whose write time is the last link" — it records *when*, never *which* worktree. So "no existing worktree holds a junction to it" cannot be evaluated from stored state; an implementer must invent a scan of every entry in `git worktree list`, joined with every project at each worktree's `HEAD`, and a junction-target comparison through `(Get-Item -Force).Target` — a lot of behaviour the plan does not describe, on a code path that deletes gigabytes. And because the stamp re-check under the lock happens *before* the delete while a worker may have linked since (the run's process is not the lock holder), a prune started between two runs of the same repo can remove an environment a slot is executing `python.exe` from. Required: either drop the worktree clause and rely on the 14-day stamp alone (then say why a live run cannot hold a stamp that old), or specify the check exactly (which command enumerates worktrees, how a junction target is compared, and what happens when the target is unreadable), and state the guard that keeps prune off an environment named in any slot ledger's grants.

**7. Severity: Major — `-ExtraEnv`/`-PathSuffix` is described two incompatible ways**
**Affected scope:** Rules *Environment variables* (line 282), Files row `Sandbox.psm1` (line 291)
**Finding & Guidance:** Line 282 says "`New-SandboxRun -ExtraEnv` takes a hashtable of names to values **plus** a `PathSuffix` string array". Line 291 says `Get-SandboxEnvironment` receives "(`-ExtraEnv`, `-PathSuffix`)" as two parameters. So: is `-PathSuffix` a separate parameter of both `New-SandboxRun` and `Get-SandboxEnvironment`, or a reserved key inside the `-ExtraEnv` hashtable? The two readings produce different parameter sets, different validation, and different Pester assertions in `Sandbox.Tests.ps1` ("`-ExtraEnv` in `Get-SandboxEnvironment`"). Also unstated: whether `-ExtraEnv` may override a baseline name (`PATH` itself, `TEMP`), and what happens when `.envs\bin` exists but `uv.exe` was deleted (line 269's recopy is `-Apply`-only, so a run can be handed a `PATH` entry that starts nothing).

**8. Severity: Major — Recopying `uv.exe` on every `-Apply` is not possible while a worker is running it**
**Affected scope:** Rules *`uv` itself* (line 269), Rule *Grant* (line 280), Risks "The copied `uv` falls behind the lockfile format" (line 119)
**Finding & Guidance:** "On every `-Apply`, the host's `uv` is copied into `.envs\bin`, replacing the old copy". `.envs\bin` is granted `(OI)(CI)RX` to a running slot's identity, and the `uv.exe` there is executed by any live worker or probe (`uv run`). Windows refuses to overwrite a mapped executable, so an `-Apply` issued during a live run (the exact case in G6: a lockfile changed while the lead is mid-phase) fails at the copy step. The plan gives no error, no ordering, and no fallback (copy to `uv-<version>.exe` and switch the `PATH` entry; or defer to the next idle `-Apply`). It also does not say whether the copy happens before or after the builds, which decides whether a failed copy aborts an otherwise valid build set.

**9. Severity: Major — Standard Readiness: the plan still has no phases or checkpoints (earlier finding still open)**
**Affected scope:** "Files" table and its closing sentence (lines 287–305); *Phasing & Checkpoints* of the Target Standard
**Finding & Guidance:** The plan is one flat file table plus "The order of work (phases and their checkpoints) is set in the plan stage, from this table" (line 305). `decisions.md` dismisses the stage-9 finding on the ground that the plan stage makes phases. As the engineer who would start coding today, that pointer is not enough to answer the two questions the order genuinely raises: `SandboxEnv.psm1` cannot be exercised before `delegate.ps1` has `-SandboxEnv`, and `delegate.ps1`'s launch path cannot link environments before `SandboxEnv.psm1` exists; and `Sandbox.psm1`'s `-EnvPaths`/`-ExtraEnv` change must land before `delegate.ps1` passes them. Required (or explicitly accepted by the orchestrator with the plan-stage artifact named as the deliverable): a five-row phase table with a "done when" per row — helpers/exports; discovery+hash+report with a fake `uv`; build/`-Apply`/`envs.json`/prune; link/unlink/grants/gate; CLI+doctor+skills+README — and say which suite each checkpoint runs (`scripts/test.ps1 -Fast` vs the full one).

**10. Severity: Major — What a build copies may not be enough for `uv` to sync a workspace**
**Affected scope:** Rules *Inputs* (line 271), Rules *Build (`lock`)* (line 272), Rules *Project path (D7)* (line 273)
**Finding & Guidance:** The build writes "the project's inputs, read with `git show <ref>:<path>`" — i.e. exactly the hash set: `uv.lock`, `pyproject.toml`, `uv.toml`, `.python-version`, `requirements*.txt`, plus each member's `pyproject.toml`. Nothing else (no member `README.md`, no `src` trees, no `[tool.hatch.build.targets.wheel].packages` paths). `uv sync --frozen --no-install-workspace` still parses the workspace and every member's `pyproject.toml`, so any member whose metadata references a missing file makes the sync fail — and the only remedy the design offers is `install-failed` with the last 20 lines of `uv`'s error (line 274), which the lead cannot act on. The motivating repo is described as "split into subprojects"; whether it is a `uv` workspace is never stated, so this hazard is unquantified. Required: say whether the private repo's root has `[tool.uv.workspace]`, and state either that a `pyproject.toml` whose `readme`/`license`/build-file references are unsatisfied is copied with those files too, or that such a project reports a distinct `unsupported (build-inputs-incomplete)` status rather than a bare `install-failed`.

## Nits

**11. Severity: Nit — Probe worktree naming: the stated non-collision reason is false.** Line 283 says "`probe-` names can't clash with task ids, which `-Cleanup` matches as `^<TaskId>-[a-z0-9]+$`". `-TaskId` allows `probe` (`^[a-z0-9][a-z0-9-]{0,48}$`), and `probe-0a1b2c3d` matches `^probe-[a-z0-9]+$`, so a `-Cleanup -TaskId probe` during a probe run would try to remove that worktree (and `canary-` has the same exposure). Say either that probe worktrees are excluded by checking the directory's `detached` state *and* a `probe-`/`canary-` name guard, or that the name gets a prefix outside the task-id alphabet.
