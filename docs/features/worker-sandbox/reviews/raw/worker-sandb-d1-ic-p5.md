# Inventive Catalyst Goldfish — REVIEW (Stage 5)

Target: `docs/designs/worker-sandbox.md`, lines 1–542.

I read the document as a fresh reviewer and audited the foundational architecture for unexamined contradictions. The design is unusually thorough: nearly every trade-off I could name has a corresponding entry in the Alternatives section (A–K) with a stated rejection rationale, and several inventive moves are already baked in (the from-scratch environment block replacing the secret denylist is a clean *Extraction*; the `patch.json` with SHA-256 is a *Blessing in Disguise*; per-worktree container SIDs are *Segmentation*; the job-object kill replacing `taskkill` is *Cheap Dispensables* for process trees).

Two contradictions survived that audit. Both are points where the author accepted a limit as a law after examining only one placement of the resolving pattern.

---

## Finding 1

1. **Severity**: Major
2. **Affected Scope**: `## Goals` (G3) and `### Alternative K: A filtering proxy for network access (G3 as first written)`.
3. **False Compromise**: The original G3 called for a per-host network allowed list. The author amended it to an all-or-nothing per-run switch and pushed the host allowlist to Future Improvements. The stated reason is in Alternative K: an AppContainer cannot connect to a proxy running *outside* it on the host's `localhost` without an admin loopback exemption, and a new SID per worktree would need admin on every run. That objection is correct for an **external** proxy — but it is the only proxy placement the author considered. The probe (cited in the Decision and in `worker-sandbox-probe`) already established that `localhost` connections *inside the same container* work without any loopback exemption. A proxy co-located in the same AppContainer as the agent process and its shell commands eliminates the loopback-exemption objection entirely, which was the load-bearing reason for amending G3. The author's second objection (the proxy would have to carry Cursor's own streaming traffic, which is "untested") remains, but it is a testing gap, not a structural impossibility — and it is strictly smaller than "no host filtering, ever."
4. **Proposed Resolution**: *Intermediary* (with *Segmentation*). Run a small allowlist proxy as a sibling process inside the same AppContainer, listening on a container-local `127.0.0.1` port. The from-scratch environment block the design already builds (Technical Plan → Launch and kill) is the natural place to set `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` so shell commands route through it; the proxy holds the host allowlist and drops everything else. Cursor's own model-server traffic either transits the same proxy (test this first — it is the open question) or, if Cursor's client refuses proxy settings, gets an explicit allow rule at the egress boundary. The result is that G3 as originally written is restored without any admin step.
5. **Secondary Liabilities**: (a) The proxy is a new in-container process to build, ship, and version alongside `Sandbox.psm1`, increasing the surface area of the runtime cache. (b) Carrying Cursor's streaming connections through a userspace proxy is genuinely untested on this stack; a regression in Cursor's auth/streaming behavior would have to be caught by the Token-refresh and Live verification checks. (c) An allowlist proxy that runs *inside* the container can still exfiltrate to any allowlisted host, so the allowlist itself becomes a security-sensitive artifact that must be reviewed (the read-list file already has this property, so the precedent exists). (d) If Cursor's client will not honor proxy env vars and must be allowed directly, the proxy model degrades to "allow Cursor's hosts + allowlisted shell hosts," which is still strictly stronger than the current all-or-nothing switch but weaker than a fully uniform allowlist.

---

## Finding 2

1. **Severity**: Nit
2. **Affected Scope**: `### Limits that stay` ("`taskkill.exe` hangs inside the sandbox. Code under test that calls it must change.") and `### Alternative` review of `taskkill` removal.
3. **False Compromise**: The design accepts that any test code (in this repo or in any other repo delegated via the `feature` skill) that invokes `taskkill.exe` must be edited before it can run sandboxed. For this repo that is fine — the design itself replaces `taskkill` in `feature.ps1` and `delegate.ps1`. But `delegate` is general-purpose: the `feature` skill calls it for arbitrary target repos, and G4 ("the workflow does not change") is asserted against `delegate`'s own regression, not against the target repos' test suites. A repo whose Pester suite or build script calls `taskkill /PID …` will fail inside the sandbox and the worker will hand the failure to the lead. The author treats this as an immutable property of AppContainers; it is actually a property of which `taskkill.exe` resolves first on `PATH`.
4. **Proposed Resolution**: *Intermediary* / *Cheap Dispensables*. Ship a tiny `taskkill.exe` shim (or a `taskkill.cmd`/`taskkill.ps1` placed earlier in the container's `PATH` than `C:\Windows\System32`) inside the runtime cache, and have `New-SandboxRun`'s `PATH` (already built from scratch in the env array) prefer it. The shim parses the subset of `taskkill`'s CLI surface that real callers use (`/PID`, `/T`, `/F`, `/IM`) and delegates to the same `[Diagnostics.Process]::GetProcessById($id).Kill($true)` the design already uses for `Stop-ProcessTree`. The container's own `taskkill.exe` in `System32` stays where it is; the shim just shadows it on `PATH`. No test code in any target repo needs to change.
5. **Secondary Liabilities**: (a) The shim must reproduce enough of `taskkill`'s exit codes and argument parsing that existing callers believe they called the real tool — incomplete coverage produces failures that look like the original hang and are harder to diagnose. (b) A second binary/script in the runtime cache is another artifact to version and another thing the patched-`node.exe` integrity story has to cover (it does not need patching, but it does need a SHA-256 in `patch.json`-style metadata, or a determined worker could replace it). (c) `taskkill /IM <name>` semantics across the container boundary differ from the real tool's global behavior; the shim must decide whether to scope kills to the job object only, and document it, or callers will get surprising results.

---

No other false compromises detected. The remaining limits I inspected (the per-Cursor-version `node.exe` re-patch, read-only `.git` with writable `worktrees\<wtName>`, per-user toolchains requiring read-list entries, capability grants outliving the feature, drive letters visible during a run, the token-refresh open question) are each either examined against an Alternative or already paired with a mitigating pattern and a removal path; they are real trade-offs, not unexamined surrenders.
