## How to run a review lens
- `pwsh -NoProfile -File skills/delegate/scripts/delegate.ps1 -Agent cursor -Profile review -Persona <lens> -Model <model> -Repo D:/cross-agent-loop -TaskId <id> -TaskFile <path>`
- **Give each reviewer its own `-TaskId`.** Two Cursor runs with the same id collide on one worktree.
- **Pass the doc by file path.** The worktree gets only committed files, so commit the doc before a run.
- **Standards:** the `implementation_readiness` persona appends its standard automatically. For `zoom_out`, paste `personas/zoom-out-standard.md` into the task file (see `fr-s8r3.md`).

- **Open product question: the `feature` skill is waterfall-shaped (raised by the user, 2026-11-12).** It front-loads design, review and gates, and the coding mostly follows the locked design. Step 6 showed the fixed cost: two two-line functions took about an hour of user time, about 30 Cursor runs, ten review lenses, a council and three gates. That fits known requirements with open implementation questions, but not features whose requirements are found by trying them (the user's game-dev experience: if the fun isn't there, pivot fast, which is why agile replaced waterfall there). Current view by size: small features use `delegate` alone with light ad hoc planning (the skill shouldn't cover them); medium features with fairly settled requirements fit the skill; large features need breaking into slices, each its own feature run, not one big locked design. Candidate changes, not decided: (1) a spike stage before design, where a worker builds a throwaway playable version the user tries; (2) review sized to risk (implementation-only review, one comprehension check, no council by default for medium features; full lenses on request); (3) cheaper pivots: a design amendment reviewed only where it changed, instead of "go back to the design" clearing every gate. Decide after the real-repo trial below, using where the process felt like overhead on an actual medium feature. **Where the weight came from (discussed 2026-11-12):** EGM set the design stage's shape (draft section by section, multi-lens review phases 5-9, resolve), the personas, standards, synthesizer and spec format, and above all the implementation-readiness **zero-decision rule** (a spec must leave the implementer no design choice): applied to every task file, it produced long task files and exhaustive test lists (D18 traces part of the 200-test suite to it), and it is why every readiness preflight found something to pin. Most of `feature.ps1` came from our own goals, not EGM: G1 plain-language entry (EGM's skills set `disable-model-invocation`, so they had to be vendored and routed), G2 resumable from disk (`state.json`, `reconcile`, pid files, killed-run handling, locks: the heaviest code), G3 recorded gates with quotes, G6 drift check at sign-off, G7 council; EGM stops at a reviewed design doc and has no build stage. Neither was forced: we chose to adopt EGM whole and set a high bar for resuming and recording. **This build was itself a medium feature run through a locked design, and is evidence for the question:** three design review rounds and a lock, yet step 6 (the first real use, in sandboxes) found seven problems no review caught (S1-S7: the `__pycache__` stop, unresolved EGM paths, lost stage in go-back records). The reviews did catch real spec gaps, but the most useful hour was the user trying it. A cheaper route would have been a rough core loop (design, plan, build, sign-off, without `reconcile` or the full lens set), used on something real, then hardened where it hurt. Questions for the redesign: whether to apply the zero-decision rule only to worker task files and not to designs, and whether small and medium features need the full EGM review at all. **Scale the zero-decision rule by model tier (user's proposal, 2026-11-12):** `code-hard` exists for tasks the lead can't fully specify, so pinning every decision there makes the lead solve the problem in the task file (sandbox A's plan even gave the worker the final code word for word). Proposal: for `code-hard`, the task file fixes the outcome (observable behaviour, acceptance tests), the boundaries (files in scope, no new dependencies) and interfaces other code depends on (signatures, data formats; critical when tasks run in parallel); internal structure, algorithms, names, internal tests and order of work are the worker's, with a short note on its choices. The readiness preflight for `code-hard` then counts a finding as a blocker only if capable implementers would differ in observable behaviour or a shared interface (today's triage rule in `delegate`'s SKILL.md, made the standard). Cost: the lead's review weighs more, so a goldfish code review becomes the norm for `code-hard`. Council: already free (seats argue; no zero-decision rule), but the question file's "options you see" can anchor them; invite options beyond the list. Evidence is thin: the one `code-hard` run (step 4, Grok, tightly specified) did well; try a two-part task template ("Decided" / "Yours to decide") on the next `code-hard` task and compare review rounds.
